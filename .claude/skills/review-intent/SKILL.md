# review-intent スキル

PR を **評価する前に、まず正しく理解する** ためのスキル。description は「作者の主張」として参考にするが、最終的な判断はコード変更の事実から行う。

## このスキルの立ち位置

- **目的**: PR が何を達成しようとしているか、コードから帰納的に把握する（理解モード）
- **既存 review 系スキルとの違い**:
  - `review_support`・`code-review:code-review`・`hr-review`・`security-review` はすべて **評価モード**（決まった観点で採点）
  - 本スキルは評価しない。事実と仮説を整理するだけ
- **理解した後で評価したい場合**: `code-review:code-review` や `hr-review` に PR を渡す

## ワークフロー

### Step 1: PR の取得

引数の有無で処理を分ける。

#### 引数あり（PR URL）

```bash
gh pr view <url> --json title,body,author,commits,files,baseRefName,headRefName
gh pr diff <url>
gh pr view <url> --comments
gh api repos/<owner>/<repo>/pulls/<number>/comments  # インラインのレビューコメント
```

#### 引数なし（現在のブランチの PR）

```bash
gh pr view --json title,body,author,commits,files,baseRefName,headRefName
gh pr diff
gh pr view --comments
# インラインコメントも見たい場合は number/owner/repo を JSON から拾って gh api を叩く
```

`gh pr view` を引数なしで実行すると、現在のブランチに紐づく PR を自動検出する。

#### コメントを取得する理由

PR には description には書かれていない重要な情報が会話で残っていることが多い。例:

- レビュアーから指摘された設計判断と、それに対する作者の回答
- 後から発覚した制約・前提の共有
- スコープ変更の合意（「○○は別 PR に分けます」など）
- 既知の不具合・TODO の宣言

これらを取りこぼすと、コードだけ見て「なぜこうなっているか分からない」誤解が生まれるため、Step 2-3 で必ず参照する。

#### PR が見つからない場合

「現在のブランチに対応する PR がありません。PR URL を引数で渡してください」と返して終了。

### Step 2: description と会話履歴を「作者・関係者の主張」として記録

`gh pr view` で取得した body の要点と、`--comments` / インラインコメントの要点をメモする。この時点では信用せず、後でコードと照合するための材料として保持する。

特に注目するもの:
- 作者自身が後から補足した内容（description に未反映の情報源）
- レビュアーとの間で合意 / 留保された設計判断
- 「これは別 PR で対応」「次の PR で直す」など、現 PR のスコープ境界を示す発言
- インラインコメントで指摘されたコード行と、その応答（fixed / wontfix など）

### Step 3: コードと会話から意図を帰納

以下の観点で `gh pr diff` の内容、関連ファイル、Step 2 で取得したコメントを精査する:

1. 領域別クラスタリング: 変更ファイルを領域ごとにグループ化
   - API / UI / データ層 / 設定・ビルド / テスト / ドキュメント / CI
2. 変更種別ごとに見る:
   - 新規追加（何のために必要になった？）
   - 削除（何を捨てた？代替は何？）
   - リネーム / 移動（命名・配置の意図は？）
   - シグネチャ変更（呼び出し側にどう影響する？）
   - 設定変更（運用や挙動が変わるか？）
3. 依存方向: import 文の変化から「誰が誰を呼ぶようになったか」を読む
4. コミット粒度・順序: 実装ストーリーを推測（土台→機能→修正、の順か等）
5. 会話との突合: コメントで言及された変更点 / 留保事項がコードに反映されているか確認
6. 必要に応じて Read / Grep: diff だけでは意図が読めない箇所は周辺コードも参照

### Step 4: 出力

下記のフォーマットでターミナルに出力する。

ユーザーフレンドリーな表示にするため以下のルールを守る:

- 出力全体を ` ``` ` などのコードフェンスで囲まない（地の Markdown として描画させる）
- `**...**`（bold）は使わない。強調は見出し・テーブル列・引用記号で代替する
- 「What」は箇条書きを羅列せずテーブルにまとめる
- 「Why」の仮説は番号と確度（中核 / 確度高 / 確度中 / 確度低）を必ず添える

````markdown
# PR #<number> 意図分析

> 一行サマリ: <コードから読み取れる「実際にやっていること」を 1 文で>

## What — コードから読み取れる事実

| 領域 | 主な変更 | 規模 |
|---|---|---|
| <領域 1> | <変更要約> | <+/- 行数 / ファイル数> |
| <領域 2> | <変更要約> | <+/- 行数 / ファイル数> |

## Why — 推定される目的（仮説）

仮説 1（中核・確度高）— <推定される目的>
- 根拠: `<file:line>` / コミット `<sha>`

仮説 2 — <推定される目的>
- 根拠: `<file:line>`

（仮説は確度高→低の順。根拠なしの推測は書かない）

## Description との照合

一致: <description にあり、コードでも確認できた点>

乖離（description に書かれていないがコードで実施）:
- <内容>

乖離（description にあるが見当たらない変更）:
- <内容>

## 会話から拾った重要事項

（コメント / インラインコメントから得られた、description には書かれていない情報。該当なしなら章ごと省略）

- <発言者・要点>: <発言の要約>（リンク: <PR コメント URL or インラインコメント箇所>）

## 著者への質問（叩き台）

1. <コード単体では意図が読めなかった箇所と、それを著者に問う形の質問>

## PR コメントへの投稿候補

1. <description に書かれていないが、レビュアーが事前に知っておくべき変更点 / 設計判断>
````

「PR コメントへの投稿候補」は、該当がなければ章ごと省略する。

### Step 5: PR コメント投稿の確認（投稿候補がある場合のみ）

「PR コメントへの投稿候補」が 1 件以上ある場合、ユーザーに確認する。

description 本文を編集（`gh pr edit --body`）するのではなく、PR コメント（`gh pr comment`）として投稿する。理由: 著者の description を上書きするのは非破壊的でなく、タイムラインにも残らないため。

```
PR にコメントとして以下を投稿しますか？
[1] <候補 1>
[2] <候補 2>
[3] <候補 3>

(yes / no / 一部選択 [番号をカンマ区切り])
```

- yes: すべて採用し、コメント本文を組み立て → `gh pr comment <url> --body "..."` で投稿
- no: 何もせず終了
- 一部選択: 採用された項目だけで本文を組み立てて `gh pr comment` で投稿

#### コメント本文のフォーマット

```markdown
## review-intent からの補足提案

description に追記しておくとレビュアーが助かる点が <N> 件あります。

1. <候補の見出し>
   - <補足の本文>

（必要なら採用してください。不要であれば無視してください）
```

#### 判断基準（候補に含めるか）

「Description との照合」で乖離として挙がった項目のうち、レビュアーが事前に知っておかないとレビューコストが大きくなるものを候補とする。以下は候補にしない:

- コミットメッセージから自明なリファクタ
- 些細なフォーマット変更
- 自動生成ファイル（`*.gen.ts` など）の機械的な追加

## 得意・不得意

### 得意
- 中規模 PR（10〜100 ファイル程度）
- 複数領域に渡る変更（API + UI + データ層など）
- description が薄い PR、テンプレ的な PR
- リネーム / 移植系の意図抽出
- 「タイトルと中身が一致していない」PR の発見

### 不得意
- 巨大 PR（200+ ファイル）— クラスタリングが粗くなる
- 外部仕様書ありき（Jira / Confluence / ADR の内容は未参照）
- 純粋なリファクタ — 意図が「綺麗にする」だけのケースは仮説が貧弱になる
- バグ修正単発 PR — 意図がほぼ description のまま

## 使い方の勘どころ

- **「Why」は仮説**。断定しない。常に「推定」「と思われる」のトーンで書く
- **description との照合は事実列挙にとどめる**。「乖離 = 悪」ではない（意図的に description を薄くしている可能性もある）
- **仮説の根拠は必ず file:line またはコミット sha で示す**
- **description への追記提案は「レビュアーが事前に知っておくと助かる」観点に絞る**
- **日本語で出力する**

## 関連スキル

理解した後の評価フェーズには以下を組み合わせる:

- `code-review:code-review` — バグ・CLAUDE.md 準拠などの一般レビュー
- `hr-review` — HR 原則チェック（メンバーデータ・AI プロンプト系の変更時）
- `security-review` — セキュリティ観点
