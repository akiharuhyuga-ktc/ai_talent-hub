# ADR-0002: デスクトップアプリ配布 — フレームワーク選定

## ステータス

proposed

## コンテキスト

本システムを非エンジニアの社内ユーザーに配布するため、React SPA をスタンドアロンのデスクトップアプリとしてパッケージングする必要がある。

### 前提条件

- **対象 OS**: macOS / Windows
- **対象ユーザー**: 非エンジニア（インストールの手軽さが重要）
- **バックエンド**: AWS 上に配置済み。デスクトップアプリにバックエンドの同梱は不要
- **フロントエンド構成**: React 19 + Vite 7 + TypeScript（SPA）
- **API 通信**: Axios で AWS 上のバックエンドと REST 通信
- **認証**: Entra ID による SSO（ADR-0001 参照）

### 先行検証: Go embed + ZIP 配布の失敗

[PR #18](https://github.com/kinto-dev/ktc-talent-hub/pull/18) で、Go バイナリに `go:embed` で React SPA を埋め込み、ZIP で配布する方式を先行検証した。技術的には動作したが、**社内セキュリティソフト（エンドポイント保護）にブロックされた**。

原因は、署名なしの実行バイナリを ZIP で展開・実行する配布形態が、社内のセキュリティポリシーに抵触したこと。この結果、以下の要件が明確になった：

1. **コード署名付きの正規インストーラー形式**（DMG / NSIS / MSI）で配布する必要がある
2. 単純なバイナリ + ZIP 配布は社内環境では実現不可能

### 要件

| 優先度 | 要件 |
|--------|------|
| 必須 | Mac / Windows 両対応のインストーラー生成 |
| 必須 | 非エンジニアが迷わずインストール・起動できる UX |
| 必須 | 既存の Vite + React プロジェクトをそのまま組み込める |
| 重要 | 配布サイズが小さい（社内ファイル共有やメール配布を想定） |
| 重要 | アプリ内自動更新の仕組み |
| 望ましい | ビルド・リリースの CI/CD 自動化が容易 |

## 検討した選択肢

### 選択肢A: Tauri v2

Rust ベースのデスクトップアプリフレームワーク。OS のシステム WebView（macOS: WKWebView、Windows: WebView2）を使用してフロントエンドを表示する。

- **最新安定版**: v2.10.3（2026-03）
- **GitHub Stars**: 約 105,000
- **バイナリサイズ**: 3〜6 MB（DMG / exe）
- **メリット**:
  - バイナリサイズが極めて小さい（Electron の 1/20 以下）
  - Vite + React の公式テンプレートあり（`create-tauri-app`）
  - DMG / NSIS (.exe) / MSI のインストーラー生成が組み込み
  - 自動更新プラグイン（`tauri-plugin-updater`）が公式提供。署名検証付き
  - セキュリティモデルが堅牢（権限の明示的な許可制）
  - GitHub Actions 向けの公式ワークフローあり
- **デメリット**:
  - ビルド環境に Rust ツールチェーンが必要（CI で対応可能）
  - OS の WebView バージョンに依存するため、CSS/JS の対応状況に差が出る可能性がある
  - Windows 10 以前では WebView2 ランタイムのインストールが必要（NSIS インストーラーが自動で処理）
  - Electron ほどエコシステム・情報量が多くない

### 選択肢B: Electron

Chromium + Node.js を同梱する、最も実績のあるデスクトップアプリフレームワーク。VS Code、Slack、Discord などが採用。

- **最新安定版**: v41.2.0（2026-04）
- **GitHub Stars**: 約 121,000
- **バイナリサイズ**: 89〜120 MB（DMG / exe）
- **メリット**:
  - Chromium を同梱するため、全プラットフォームで描画が完全に一致する
  - エコシステムが最も大きく、情報・プラグインが豊富
  - electron-builder / Electron Forge による成熟したビルドツール
  - `electron-updater` による自動更新が安定・実績豊富
  - WebView 互換性の問題が一切ない
- **デメリット**:
  - バイナリサイズが大きい（89〜120 MB）。社内配布時の負担
  - メモリ消費が多い（Chromium プロセスが常駐）
  - Chromium のセキュリティアップデートへの追従が必要

### 選択肢C: Wails v2

Go ネイティブのデスクトップアプリフレームワーク。Go でバックエンドロジックを書き、システム WebView でフロントエンドを表示する。

- **最新安定版**: v2.12.0（2026-03）、v3 はアルファ段階
- **GitHub Stars**: 約 34,000
- **バイナリサイズ**: 約 4 MB（単一バイナリ）
- **メリット**:
  - Go プロジェクトとの親和性が高い（本リポジトリのバックエンドは Go）
  - バイナリサイズが小さい
  - Go の `embed.FS` でフロントエンド資材を単一バイナリに埋め込み
  - Vite + React テンプレートあり
- **デメリット**:
  - **自動更新機能がない**（自前実装が必要）
  - **インストーラー生成機能がない**（DMG / NSIS を別途ツールで作成する必要がある）
  - バックエンドを AWS に置く方針のため、Go 統合のメリットが薄い
  - ローカルにバックエンドがなくても Go プロセスが必ず起動する
  - コミュニティが Tauri / Electron に比べて小さい
  - v3 への移行時期が不透明

### 選択肢D: Go embed + ZIP 配布（検証済み・却下）

Go バイナリに `go:embed` で React SPA を埋め込み、単一実行ファイルとして ZIP 配布する方式。[PR #18](https://github.com/kinto-dev/ktc-talent-hub/pull/18) で検証済み。

- **バイナリサイズ**: 約 8 MB（ZIP 圧縮後 約 4 MB）
- **メリット**:
  - 実装がシンプル（Go 標準ライブラリのみ）
  - 単一ファイル配布で依存なし
  - ダブルクリックで起動 → ブラウザで利用可能
- **デメリット（致命的）**:
  - **社内セキュリティソフトにブロックされた**（署名なしバイナリの ZIP 展開・実行が検知対象）
  - コード署名の仕組みがない
  - 正規のインストーラー形式（DMG / NSIS）を生成できない
  - 自動更新機能がない

**結論: 社内セキュリティポリシーにより採用不可。**

## 決定

**選択肢A: Tauri v2** を採用する。

## 理由

### 1. 社内セキュリティ要件を満たすインストーラー・コード署名

PR #18 の検証で、署名なしバイナリの ZIP 配布は社内セキュリティに引っかかることが判明した。Tauri v2 は DMG / NSIS / MSI の正規インストーラー生成とコード署名に対応しており、この要件をクリアできる。Wails v2 にはこの機能がなく、選択肢から外れる。

### 2. 非エンジニアへの配布に最適なサイズ

社内ファイル共有やメールで配布する想定では、**3〜6 MB（Tauri）と 89〜120 MB（Electron）の差は大きい**。ダウンロード時間・ストレージの観点で、非エンジニアの UX に直接影響する。

### 3. 配布に必要な機能が組み込み

| 機能 | Tauri v2 | Electron | Wails v2 |
|------|----------|----------|----------|
| インストーラー生成 | 組み込み（DMG, NSIS, MSI） | 組み込み（electron-builder） | なし（要自前） |
| 自動更新 | 公式プラグイン | electron-updater | なし（要自前） |
| コード署名 | 対応 | 対応 | 要手動設定 |

Wails はインストーラーと自動更新の両方が欠けており、非エンジニア配布には不向き。

### 4. 既存 Vite + React プロジェクトとの統合が容易

Tauri は Vite を公式にサポートしており、既存の `frontend/` ディレクトリに `src-tauri/` を追加するだけで導入できる。既存のビルドパイプライン（`vite build`）はそのまま利用可能。

### 5. バックエンドが AWS にあるため Go 統合は不要

Wails の最大のメリットである Go 統合は、バックエンドを AWS に配置する方針（ADR-0001 のプロキシサーバー構成）により活かせない。

### 6. WebView 依存のリスクは許容範囲

Tauri が使用する WebView2（Windows）/ WKWebView（macOS）は、対象 OS で十分にモダンなバージョンが提供されている。本アプリは社内向けであり、OS バージョンを一定以上に制限できるため、互換性リスクは低い。

## 影響

- `frontend/` 配下に `src-tauri/` ディレクトリ（Tauri 設定 + Rust ボイラープレート）が追加される
- CI/CD に Rust ツールチェーンのセットアップが必要（GitHub Actions の `tauri-apps/tauri-action` で対応）
- API のベース URL を環境に応じて切り替える仕組みが必要（開発時: localhost、本番: AWS エンドポイント）
- Windows ビルドのクロスコンパイルは困難なため、CI で Mac / Windows のマトリクスビルドを構成する
- Rust のコードを直接書く必要はほぼない（設定ファイルの変更が中心）
