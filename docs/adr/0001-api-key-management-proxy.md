# ADR-0001: Claude API キー管理 — プロキシサーバー方式の採用

## ステータス

accepted（2026-04-24 改訂: AWS 環境の具体構成を反映、Bizport `/me` 経由の認証方式に確定）

## コンテキスト

本システムは Claude API を使用して AI 機能を提供する。
現在、API キーは `.env.local` の環境変数で管理しているが、以下の課題がある。

### 課題

1. **スタンドアロン配布との相性が悪い**
   - 本システムは非技術者にデスクトップアプリ（Tauri v2、ADR-0002）として配布する想定
   - 利用者それぞれに API キーを取得・設定してもらうのは現実的ではない

2. **API キーの漏洩リスク**
   - バイナリに埋め込めば全利用者に同じキーが渡る
   - 環境変数で管理するにしても、非技術者への説明コストが高い

3. **利用者の特定ができない**
   - 現在の仕組みでは誰が API を呼んだか追跡できない
   - コスト管理・不正利用の検知が困難

## 検討した選択肢

### 選択肢 A: 利用者ごとに API キーを配布

- メリット: シンプル。追加インフラ不要
- デメリット:
  - 非技術者にキー設定を求めるのが非現実的
  - キーの回収・ローテーションが困難
  - 誰がどれだけ使ったか追跡しにくい

### 選択肢 B: プロキシサーバー + JWT 認証

- メリット:
  - 利用者は API キーを意識しない（社内 SSO でログインするだけ）
  - API キーはプロキシサーバーのみが保持（漏洩リスク最小化）
  - JWT から利用者を特定できる（監査・コスト配分が可能）
  - 許可された人だけが API 利用可能（アクセス制御）
  - 既存の社内認証基盤（Entra ID / Bizport）をそのまま活用
- デメリット:
  - プロキシサーバーの構築・運用が必要
  - ネットワーク経由のため、オフライン利用不可
  - 追加のインフラコスト

### 選択肢 C: バイナリに API キーを埋め込み + 難読化

- メリット: オフライン動作可能。インフラ追加なし
- デメリット:
  - リバースエンジニアリングでキーが抽出される
  - 全利用者が同一キーを共有（漏洩時の影響大）
  - 利用者の特定不可能

## 決定

**選択肢 B: プロキシサーバー + JWT 認証** を採用する。

### 具体構成（2026-04-24 確定）

- プロキシ: **AWS CloudFront + Lambda**
- AI モデル提供: **AWS Bedrock**（Claude）
- 認証: **既存 Bizport の `/me` エンドポイントに Entra ID JWT を投げて検証**

## 理由

1. **スタンドアロン配布の UX を損なわない**
   - 利用者はアプリを起動 → Entra ID でログイン → すぐ使える
   - API キーの設定は一切不要

2. **セキュリティ要件を満たす**
   - 人事データを扱うシステムとして、利用者認証は必須
   - API キーの一元管理で漏洩リスクを最小化
   - Bizport の認証基盤に乗ることで、入退社などのユーザーマスタ変動が自動的に反映される

3. **Bizport `/me` を信頼境界に再利用する**
   - Lambda 側で Entra ID 直接統合（OIDC / JWKS 検証）を実装しない
   - 既存の Bizport が信頼できる認証層として動いているので、認可ロジックを二重実装しない
   - 認証実装ミスのリスクを下げる
   - `/me` が返すユーザー情報を Lambda のログに残せば、誰が使ったかの監査も可能

4. **既存インフラとの整合性**
   - 社内の AWS インフラ・Bizport 認証に統一できる

## アーキテクチャ

```
┌──────────────────┐                          ┌─────────────────────────────────┐
│ Tauri デスクトップ │                          │             AWS                 │
│  アプリ (SPA)     │                          │                                 │
│                  │                          │   CloudFront                    │
│                  │  ① JWT 付き API 呼び出し   │        ↓                       │
│                  │ ───────────────────────→ │   Lambda                        │
│                  │                          │        │                        │
│                  │                          │        │ ② JWT を /me に投げる   │
│                  │                          │        ↓                        │
│                  │                          │   ┌──────────┐                  │
│                  │                          │   │ Bizport  │ (Entra ID 検証)  │
│                  │                          │   │  /me     │                  │
│                  │                          │   └──────────┘                  │
│                  │                          │        │                        │
│                  │                          │        │ ③ 認証 OK              │
│                  │                          │        ↓                        │
│                  │                          │   Lambda                        │
│                  │                          │        ↓ Bedrock 呼び出し        │
│                  │                          │   Bedrock (Claude)              │
│                  │  ④ AI レスポンス           │                                 │
│                  │ ←─────────────────────── │                                 │
└──────────────────┘                          └─────────────────────────────────┘
```

### 認証フロー

1. ユーザーがアプリを起動し、Entra ID（社内 SSO）でログイン → JWT を取得
2. アプリは JWT を付けて CloudFront 配下の Lambda にリクエスト
3. Lambda は受け取った JWT を Bizport の `/me` エンドポイントに投げて検証
4. `/me` が 200 + ユーザー情報を返したら、Lambda は AWS Bedrock に Claude API リクエスト
5. Bedrock のレスポンスをアプリに返却

## 影響

- AWS インフラ（CloudFront / Lambda / Bedrock）の構築・運用が必要
- Bizport `/me` の SLA・レイテンシに依存する
  - 毎リクエスト都度検証するか、Lambda 側で短時間 JWT キャッシュを持つかは別途検討
  - Bizport 側の障害が AI 機能停止に直結する点をモニタリング対象に含める
- アプリはオンライン前提になる（AI 機能利用時）
- `.env.local` の API キー設定は開発者向けのみとなり、エンドユーザーには不要
- AWS 側のコスト管理（Bedrock 利用量 + Lambda + CloudFront）が必要
